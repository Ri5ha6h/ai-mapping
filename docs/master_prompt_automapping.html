Master Prompt for Codex: Auto Mapping SaaS POC

Use this document as the master build prompt for creating a phased POC of an AI-assisted Auto Mapping SaaS for logistics and supply chain integrations. The POC must prove that source and target samples can be analyzed, mapped, reviewed, edited, executed deterministically, validated, and saved as reusable mapping templates.

Primary POC focus: JSON, XML, and basic inbound EDI 214 / EDI 856 samples. CSV, PDF/IDP, authentication, multi-tenancy, 5GB streaming, partner guides, and iPaaS connectors are intentionally deferred.

1. The Master Prompt to Give Codex

Copy the full prompt below into Codex:

You are building a phased POC for an AI-assisted Auto Mapping SaaS targeted at logistics and supply chain integration teams.

The goal is to build a full-stack POC with:
- Backend: Python 3.14.5 + FastAPI 0.136.3 + Pydantic 2.13.4 + Uvicorn 0.49.0
- Backend quality and tests: pytest 9.0.3, httpx 0.28.1, respx 0.23.1, Ruff 0.15.16, and Pyright 1.1.410
- Backend parser/runtime helpers: orjson 3.11.9 where useful, defusedxml 0.7.1 for safe XML parsing, and lxml 6.1.1 only if richer XML writing is needed
- Backend AI provider: optional OpenRouter integration through direct httpx REST calls when OPENROUTER_API_KEY is configured
- Frontend: TanStack Start + React + TypeScript
- UI system: shadcn/UI using Base UI primitive support
- Frontend data/API workflows should use Effect for typed async flows, decoding, retries, and structured errors
- Transformation expression layer: JSONata where possible
- Supported structured formats for POC: JSON and XML
- EDI support for POC: basic inbound EDI 214 and EDI 856 parsing into canonical JSON
- Output formats for POC: JSON and XML
- Execution model for POC: synchronous
- Authentication and multi-tenancy: not required for POC
- CSV: explicitly out of scope
- PDF, scanned images, email extraction, IDP, and multimodal extraction: out of scope
- 5GB streaming architecture: out of scope for implementation, but design code boundaries so that streaming support can be added later
- Partner-facing implementation guides, webhooks, iPaaS connectors, and event orchestration: out of scope for the first POC

The POC must prove:
1. A user can upload or paste source data.
2. A user can upload or paste target sample data.
3. The system can infer source and target schemas.
4. The system can generate suggested mappings using a blend of:
   - rule-based heuristics
   - optional OpenRouter integration if OPENROUTER_API_KEY is provided
5. The user can review and edit mappings visually.
6. The user can edit the advanced JSONata expression directly.
7. The deterministic backend can execute the mapping.
8. The output can be generated as JSON or XML.
9. Validation errors are shown clearly.
10. A mapping template can be saved with versions.

Build the project in phases. Each phase must be reviewable and testable end to end before moving to the next phase.

Important architectural principle:
AI is only a design-time assistant. AI may suggest mappings, JSONata expressions, transformations, or schema hints. AI must not be the production transformation runtime. The transformation runtime must be deterministic.

Frontend/backend boundary:
Use TanStack Start as the frontend app shell, routing, and build framework only. FastAPI remains the only product backend for parsing, schema inference, mapping suggestions, transformation execution, validation, and mapping templates. Do not introduce TanStack Start server functions for product/domain APIs in the POC.

Backend stack boundary:
Target Python 3.14.5 for the POC. If a niche parser or runtime dependency fails on Python 3.14.5, document the issue and fall back to Python 3.13.x only for compatibility. Do not add the openai package as a backend dependency unless a later implementation explicitly chooses an SDK adapter.

Use a canonical internal JSON representation. All source formats should be parsed into canonical JSON before mapping. Target writers should then serialize the mapped result into JSON or XML.

For the POC, prefer clarity and inspectability over enterprise-scale optimization.

2. Product Context

The product is an Auto Mapping Service for logistics and supply chain enterprises. The long-term SaaS platform may include Auto Mapping, Parcel Solutions, and Scraping Services, but this POC only covers Auto Mapping.

Positioning: AI-assisted data mapping and transformation engine for logistics integrations.

Initial users are developers, integration engineers, and integration analysts. Later versions may support non-technical users with more guided workflows.

4. Architecture Direction

The high-level flow should be:

Source Input
  -> Format Parser
  -> Canonical JSON
  -> Mapping Suggestion Engine
  -> Visual Mapping Editor / JSONata Editor
  -> Deterministic Mapping Runtime
  -> Validation Engine
  -> JSON or XML Output
  -> Save Versioned Mapping Template

Core Design Rules

  • Never use AI as the execution runtime.
  • Always parse source data into canonical JSON first.
  • Keep parser, mapper, validator, and writer layers separate.
  • Keep interfaces clean so 5GB streaming can be added later.
  • Keep mapping templates portable and versioned.
  • Allow both visual editing and advanced JSONata editing.

5. JSONata and Mapping Model

Use JSONata as the transformation expression layer wherever practical. Do not expose only raw JSONata. The UI should maintain a structured mapping model that can be rendered visually and can also store the advanced JSONata expression.

Mapping Template Model

{
  "template_id": "shipment-status-template",
  "name": "Shipment Status Mapping",
  "description": "Maps logistics shipment status source payload to target API payload.",
  "active_version": 1,
  "versions": [
    {
      "version": 1,
      "source_format": "xml",
      "target_format": "json",
      "source_schema_snapshot": {},
      "target_schema_snapshot": {},
      "mapping_spec": {
        "engine": "jsonata",
        "rules": [
          {
            "id": "rule_001",
            "type": "field",
            "source_path": "$.shipment.trackingNumber",
            "target_path": "$.tracking.number",
            "required": true,
            "confidence": 0.94,
            "jsonata": "{ \"tracking\": { \"number\": shipment.trackingNumber } }"
          }
        ],
        "full_jsonata_expression": "{ \"tracking\": { \"number\": shipment.trackingNumber } }"
      },
      "validation_rules": [
        {
          "type": "required",
          "path": "$.tracking.number",
          "message": "Tracking number is required."
        }
      ],
      "created_at": "2026-06-08T00:00:00Z"
    }
  ]
}

Rule Types to Support in POC

  • field: direct source path to target path mapping
  • constant: hardcoded value into target path
  • concat: combine multiple source values
  • date_format: basic date formatting
  • condition: simple if/then mapping
  • loop: basic array mapping for clean arrays
Implementation guidance: If complete JSONata execution is too heavy in the first pass, implement a deterministic rule executor first and still keep JSONata as editable/generated metadata. Then add JSONata execution as the next step.

6. EDI Handling

EDI is important for logistics, but the POC should not attempt a full EDI translator. It should support basic parsing for two inbound transaction types:

  • EDI 214: Transportation Carrier Shipment Status Message
  • EDI 856: Advance Ship Notice

POC EDI Flow

EDI sample
  -> Basic segment parser
  -> Canonical JSON
  -> Source schema inference
  -> AI/rule-based mapping suggestions
  -> Mapping execution
  -> JSON or XML output

EDI POC Constraints

  • Support common segment recognition only.
  • Do not build a full X12 compliance engine.
  • Do not generate outbound EDI.
  • Do not validate against full implementation guides.
  • Preserve raw segment data for debugging.

Canonical EDI JSON Shape Example

{
  "edi": {
    "transaction_set": "214",
    "segments": [
      {
        "segment_id": "B10",
        "elements": ["123456", "TRACK123", "CARRIER"]
      },
      {
        "segment_id": "L11",
        "elements": ["REF123", "BM"]
      },
      {
        "segment_id": "AT7",
        "elements": ["X3", "NS", "", "", "20260608", "1030", "LT"]
      }
    ],
    "raw": "ISA*...~GS*...~ST*214*...~"
  }
}

7. Backend Requirements

Tech Stack

  • Python 3.14.5 as the target runtime, with Python 3.13.x allowed only as a documented compatibility fallback.
  • FastAPI 0.136.3 for the API layer.
  • Pydantic 2.13.4 for request, response, template, schema, and validation models.
  • Uvicorn 0.49.0 for local ASGI development.
  • pytest 9.0.3 for backend tests.
  • httpx 0.28.1 for tests and direct OpenRouter REST calls.
  • respx 0.23.1 for mocking external OpenRouter calls in tests.
  • Ruff 0.15.16 for linting and formatting checks.
  • Pyright 1.1.410 for backend type checking.
  • orjson 3.11.9 where useful for JSON response or serialization performance.
  • defusedxml 0.7.1 for safe XML parsing.
  • lxml 6.1.1 only if richer XML writing is needed beyond the standard library.
  • Optional OpenRouter integration through direct httpx REST calls when OPENROUTER_API_KEY is configured.
Backend dependency boundary: do not add the openai package for the POC. Optional AI mapping suggestions should use OpenRouter behind the ai_suggester provider interface with OPENROUTER_API_KEY. Also support optional OPENROUTER_MODEL, OPENROUTER_HTTP_REFERER, and OPENROUTER_APP_TITLE environment variables.

Parser and Runtime Guidance

  • Use the standard library json first; use orjson only where it materially improves response or serialization paths.
  • Use defusedxml for safe XML parsing and add lxml only when richer XML writing is required.
  • Keep JSONata-compatible expressions in mapping templates, but use deterministic Python rule execution as the first runtime path.
  • Treat Python jsonata 0.2.5 as optional and experimental if added later.
  • Use a custom lightweight X12 segment parser for EDI 214 and EDI 856. Do not depend on full EDI engines for the POC.

API Endpoints

Endpoint Purpose
POST /api/parse Parse raw JSON, XML, or EDI into canonical JSON.
POST /api/schema/infer Infer schema from canonical JSON.
POST /api/mappings/suggest Generate mapping suggestions using rule-based logic plus optional AI.
POST /api/transform Execute mapping synchronously and return output.
POST /api/validate Validate output against target schema and mapping rules.
POST /api/templates Save a mapping template.
GET /api/templates List saved templates.
GET /api/templates/{template_id} Read one template with its versions.
POST /api/templates/{template_id}/versions Create a new version of a saved mapping template.

Validation Errors to Support

  • Invalid source format
  • Invalid target sample format
  • Missing source path
  • Unmapped required target field
  • Type mismatch
  • Failed transformation
  • Invalid JSONata expression
  • Output does not match inferred or edited target schema

AI Blend Requirement

Implement mapping suggestion in two layers:

  1. Rule-based suggester: compares field names, normalized names, path endings, common logistics synonyms, and primitive types.
  2. Optional OpenRouter suggester: if OPENROUTER_API_KEY is available, send source schema, target schema, and domain context to OpenRouter through direct httpx REST calls and request mapping suggestions. If no key is available, the app must still work using the rule-based suggester.

Storage

For POC, simple local JSON file storage is acceptable. Keep repository abstraction so PostgreSQL can be added later.

  • Node.js LTS with pnpm for frontend package management.
  • TanStack Start as the React app shell, routing, and build framework.
  • React and TypeScript for all frontend UI and domain modeling.
  • TanStack Router through TanStack Start for route structure.

Frontend boundary: shadcn/UI components should be copied into the project and treated as editable local UI code. Base UI primitive support is required by the scaffold or preset, not a later optional swap. TanStack Start must not own product/domain APIs; all parser, mapping, transformation, validation, and template calls go to FastAPI through the Effect-backed API layer.

Build one main workbench page with the following panels:

  • Source input panel: paste/upload source data and choose source format.
  • Target input panel: paste/upload target sample and choose target output format.
  • Parse and infer schema button.
  • Auto map / AI map button.
  • Source schema viewer.
  • Target schema viewer.
  • Visual mapping editor.
  • Advanced JSONata editor.
  • Validation panel.

UX Requirements

  • Users should clearly see source fields and target fields.
  • Suggested mappings should show confidence score.

9. Phased Build Plan

Phase 1: Backend Foundation

  • Create FastAPI backend with Python 3.14.5, FastAPI 0.136.3, Pydantic 2.13.4, Uvicorn 0.49.0, pytest 9.0.3, Ruff 0.15.16, and Pyright 1.1.410.
  • Add parsers for JSON and XML.
  • Add basic EDI segment parser.
  • Add canonical JSON output.
  • Add schema inference.
  • Add unit tests for parsing and schema inference.
Review checkpoint: Parse JSON, XML, EDI 214, and EDI 856 samples into canonical JSON.

Phase 2: Mapping Suggestion Engine

  • Create rule-based mapping suggestion engine.
  • Add common logistics synonyms such as tracking number, shipment id, carrier, event code, date, location, quantity, item, container, order.
  • Add optional OpenRouter suggestion provider behind an interface using httpx and OPENROUTER_API_KEY.
  • Return mapping suggestions with confidence scores.
Review checkpoint: Given source and target schemas, system returns useful mapping suggestions.

Phase 3: Deterministic Transformation Runtime

  • Implement mapping execution.
  • Support field mapping, constants, concat, date formatting, simple condition, and basic loop.
  • Add JSON output writer.
  • Add XML output writer.
  • Add validation errors.
Review checkpoint: Execute JSON to JSON, XML to JSON, JSON to XML, and EDI-derived JSON to JSON/XML.

Phase 4: Frontend Mapping Workbench

  • Create TanStack Start frontend using pnpm and the shadcn/UI start template with Base UI support.
  • Route all frontend FastAPI calls through the Effect-backed API layer.
  • Add source and target input panels.
  • Add schema viewers.
  • Add mapping suggestion table/editor.
  • Add advanced JSONata editor.
  • Add output preview and validation panel.
Review checkpoint: User can perform the full mapping flow from UI.

Phase 5: Template Versioning

  • Add local template repository.
  • Save mapping templates.
  • Create new template versions.
  • Load existing templates back into the editor.
Review checkpoint: User can save, reload, and version mappings.

Phase 6: Polish and Demo Scenarios

  • Add sample data files.
  • Add clear empty states and error states.
  • Add README with setup instructions.
  • Add demo script for XML to JSON and EDI 214/856 to JSON/XML.
Review checkpoint: POC can be demoed end to end.

10. Acceptance Criteria

  • App starts locally with clear README instructions.
  • Backend and frontend run separately during development.
  • User can paste JSON source and JSON target sample, generate mapping, edit it, run it, and see JSON output.
  • User can paste XML source and JSON target sample, generate mapping, edit it, run it, and see JSON output.
  • User can paste JSON source and XML target sample, generate mapping, edit it, run it, and see XML output.
  • User can paste basic EDI 214 and convert it to canonical JSON.
  • User can paste basic EDI 856 and convert it to canonical JSON.
  • User can map EDI-derived canonical JSON to JSON or XML target output.
  • User can see validation errors for missing required fields, invalid paths, invalid formats, and transformation failures.
  • User can save a mapping template and create a new version.
  • OpenRouter integration is optional. The system must still work without an API key.
  • AI is never required for deterministic execution.
