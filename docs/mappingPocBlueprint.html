SaaS Auto Mapping Service: POC Strategic Blueprint

Project Context: This document serves as a comprehensive system summary containing all architectural constraints, scope limits, and design decisions finalized for the upcoming Proof of Concept (POC). It is formatted specifically to guide deep LLM reasoning and code-generation preparation.

1. Executive Summary & Core Philosophy

The objective is to build an Auto Mapping Service SaaS tailored for the logistics and supply chain sector. Logistics data is historically disjointed, messy, and locked behind varying legacy formats.

The core philosophy of this platform hinges on a critical architectural boundary: AI is utilized exclusively as a design-time assistant (inferring schemas, mapping logic, and creating templates), while a deterministic execution engine runs the actual production data transformations. This ensures 100% predictable, low-latency, and cost-effective operations.

2. POC Scope Boundaries

In-Scope (What We Are Building Now)

  • Design Engine Focus: Real-time mapping generation inside a UI framework.
  • Small File Sizes: Standard payloads strictly capped between 5MB to 10MB.
  • Format Horizon: JSON, XML, and basic EDI concepts.
  • Structural Routing: Map field paths from Point A to Point B across different schemas.
  • Basic Transformations: Native support for string concatenation, basic date string formatting, and hardcoded default constants.
  • Python Foundations: Lightweight execution using pure Python scripts.

Out-of-Scope (Deferred to Post-POC)

  • 5GB Streaming Architectures: High-volume chunk-based file streaming and async chunking pipelines.
  • CSV Support: Flattening hierarchical layers or handling missing array boundaries (deferred).
  • Custom DSL Parsing: Building a proprietary execution compiler from scratch.
  • Advanced Logic: Complex multi-conditional looping or programmatic code injections.

3. The Data Transformation Pipeline

To avoid scaling problems, the architecture converts all incoming formats into a centralized, canonical baseline structure before processing.

Source File → Open-Source EDI/XML Parsers → Canonical Internal JSON → Lightweight Engine + Mapping Spec → Target Output
  1. Parser Phase: Files (XML or EDI) are converted immediately to a Standard Python Dictionary (Canonical JSON equivalent). EDI files will leverage open-source libraries (e.g., parsing tools with established segments) to output raw XML first, which is then mapped to the Canonical JSON format.
  2. Design Phase (UI): The AI analyzes a tiny source sample and target sample, recognizes semantic discrepancies (e.g., matching DTM*011 or ship_dt to deliveryDate), and crafts a JSON Mapping Specification.
  3. Execution Phase (Engine): A fast, lightweight custom Python script processes the Canonical JSON input, applies the JSON Mapping Specification, executes mutations, and structures the output.

5. JSON Mapping Specification Definition (The DSL)

The AI must generate a clean, JSON-based specification that declares exactly how keys are mapped and what native functions should change the underlying data values. Below is the structural layout required for the engine: 

{
  "specification_version": "1.0",
  "mappings": [
    {
      "type": "direct",
      "source_path": "order.header.id",
      "target_path": "transactionId"
    },
    {
      "type": "transform",
      "transform_type": "CONCATENATE",
      "source_paths": ["order.customer.firstName", "order.customer.lastName"],
      "target_path": "customer.fullName",
      "parameters": {
        "delimiter": " "
      }
    },
    {
      "type": "transform",
      "transform_type": "DATE_FORMAT",
      "source_path": "order.dates.creation_dt",
      "target_path": "metadata.processedAt",
      "parameters": {
        "input_format": "YYYYMMDD",
        "output_format": "YYYY-MM-DD"
      }
    }
  ]
}

6. Core Edge Cases & Guardrails to Research

  • Schema Inference Fallbacks: If the user targets fields with zero contextual or semantic overlap, the engine must flag unmapped variables back to the UI, allowing the user to manually draw links or pass clarifying prompts down to the AI model.
  • Validation Checks: The design UI must require a formal user confirmation before saving the mapping template. This places human verification at the center of the lifecycle, mitigating data errors in downstream logistics operations.
  • Array/Loop Constraints: For the POC, collections of repeating records are expected to be clean arrays capped at 50 to 100 simple records, keeping structure depths shallow.
